Eliminating Periodic Scraping Signatures with Randomized systemd Timers and Decoy Traffic

Why fixed cron intervals get flagged even with clean browser fingerprints, and how a master systemd timer interleaving local-LLM decoy queries breaks periodicity.

Modern anti-bot systems do not rely solely on TLS handshakes or headless browser flags. Even if you use a patched browser binary like cloak-browser with realistic viewport dimensions and clean residential routing, a server-side behavioral model will still flag a client that requests the exact same three product URLs every 30 minutes on the dot.

While building my Autonomous E-Commerce Price Tracker, fixing TLS and DOM fingerprinting solved day-one blocks, but week-long reliability required dismantling temporal and behavioral patterns.

1. Moving from Fixed Cron Schedules to Jittered systemd Timers

Traditional cron entries execute at predictable wall-clock boundaries (*/30 * * * *). Replacing cron with a master systemd timer configured with AccuracySec=1s and a large RandomizedDelaySec spreads executions across irregular intervals, while a Python orchestrator enforces exponential backoff and quiet hours overnight when human traffic drops.

[Unit]
Description=Orchestrate randomized price check and decoy queue

[Timer]
OnBootSec=4m
OnUnitActiveSec=42m
RandomizedDelaySec=28m
Persistent=true

[Install]
WantedBy=timers.target

2. Interleaving Decoy Sessions via a Local LLM

A session that loads a deep product link, reads the price node, and immediately closes looks nothing like a shopper. To blend real threshold checks into organic browsing noise:

  • URL Sanitization: Before queuing any target link, the daemon strips affiliate, referral, and session-tracking query parameters so runs do not link back to a single shared URL signature.
  • Decoy Query Generation: A lightweight local LLM generates plausible category browse paths and comparison queries related to the product domain. The scheduler interleaves these decoy navigations—complete with variable scroll pauses—around real target checks.

3. Decoupling Scraping from Alert Delivery

The scraping daemon writes normalized price observations into SQLite/SQL and exits immediately. A separate lightweight evaluator compares the latest observation against user-defined thresholds and triggers a Firebase Cloud Messaging (FCM) push payload to the Android app only on state transitions—keeping the browser worker stateless and resilient to transient network drops.
