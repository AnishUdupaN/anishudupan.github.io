Routing Compute Workloads Across Heterogeneous LAN Nodes Without a Heavy Cluster Manager

Notes on building a lightweight master-worker orchestrator in Python: capability discovery, heartbeat timeouts, and avoiding head-of-line blocking on mixed hardware.

When a lab or small team has three laptops, an older desktop with a discrete GPU, and a headless Linux box sitting on the same local network, pooling their compute usually forces an uncomfortable choice: spend days configuring Kubernetes or Slurm, or manually SSH into each machine and copy files around.

While building our Distributed Computing System for Heterogeneous Computers, we wanted a zero-configuration control plane that treats hardware differences as a first-class scheduling constraint rather than assuming uniform worker nodes.

1. Why Uniform Round-Robin Fails on Mixed Hardware

Standard round-robin or naive queue-pulling breaks down quickly when nodes have asymmetric capabilities:

  • Hardware acceleration mismatch: Dispatching a matrix-heavy or inference task to a CPU-only ultrabook stalls the entire batch while a CUDA-capable desktop sits idle two seconds later.
  • Thermal throttling under sustained load: Laptops boost aggressively for 20 seconds and then drop clock speeds by 40%. Static benchmark scores collected once at startup become stale mid-run.
  • Asymmetric network bandwidth: A node connected over 2.4 GHz Wi-Fi becomes a bottleneck if assigned data-heavy payloads better suited for wired Gigabit Ethernet peers.

2. Telemetry-Weighted Task Routing

Instead of static node weights, each worker daemon publishes a lightweight telemetry frame alongside its periodic heartbeat:

{
  "node_id": "worker-02",
  "accelerators": ["cuda:sm_86"],
  "cpu_free_pct": 74.2,
  "ram_free_mb": 6140,
  "active_tasks": 1,
  "avg_task_latency_ms": 412
}

When a job enters the master queue, it declares hard constraints (required accelerator tags, minimum free RAM, container runtime availability) and a soft compute profile. The scheduler filters out ineligible nodes first, then scores remaining candidates using current free memory, active queue depth, and rolling task completion latency.

3. Heartbeats and Idempotent Failover

Consumer machines sleep, lose Wi-Fi, or get rebooted mid-execution. Every dispatched task is assigned a lease ID and an input payload hash. If a worker misses three consecutive heartbeat intervals, the master marks its active lease expired and requeues the task onto the next highest-scoring node.

Design rule: Workers write intermediate outputs to a job-scoped staging directory and commit results atomically only upon completion. If a delayed worker reconnects after its lease has already been reassigned, the master rejects the stale commit token cleanly.

4. Packaging Dependencies with Docker

Heterogeneous operating systems and Python environments are the fastest way to break distributed execution. Wrapping task runners inside slim Docker images—selecting CPU or GPU base variants automatically based on the worker's capability advertisement—kept execution deterministic across machines without manual dependency setup on every host.
